У меня в проекте `full_username` состоит из `username|created=date|days=count|exp=date`, при несовпадении с этим форматом адекватная работа скриптов не гарантируется, это сделано что бы не создавать отдельную базу пользователей и просто всю техническую информацию в прямо в `full_username` в `config.json`, дубль `full_username` не возможен, `xray` даже не запустится, по этому во избежание ошибок в работе добавить даже дубль `username` через скрипты нельзя, что бы при изменении дат не стали совпадать `full_username`. 


**Работа с дублями имен пользователей**

***Добавление дублей username:***

Добавить два одинаковых `username` невозможно, только если отредактировать `config.json` вручную можно добавить такой же `username` с другими датами.

***Удаление дублей username:***

!!! надо проверить удаляет ли задвоения в инбаунде и блоке, должен удалять везде
!!!!!   только удалить, скрипт удаляет все даже если юзера нет в инбаундах а есть только в блоке

***Блокировка дублей username:***

Если отредактировать `config.json` вручную и добавить дубль `username` то при срабатывании авто блокировок его будет без проблем блокировать:
- по времени блокирует индивидуально каждый `full_username` отдельно
- по трафику блокирует по всем совпадениям `username`
- при ручной блокировке дубля `username` будет ошибка и предложение убрать дубли через редактирование конфигурации `xray`

***Разблокировка дублей username вручную:***

- разблокировать вручную не получится будет ошибка и предложение убрать дубли через редактирование `config.json`
- добавить ему времени и сбросить блок по времени не получится будет ошибка и предложение убрать дубли через редактирование `config.json`.
- сброс трафика и убрать блок по трафику не получится будет ошибка и предложение убрать дубли через редактирование `config.json`.
При ручных разблокировках идет проверка задвоений в `config.json` - `inbound` и `config.json` - `blocked ruletag`. При дублях `username` только ручное редактирование `config.json`, это зделано для того что бы мы не разблокировали непонятного кого, скрипт добавления нам не даст просто так добавить дубликат, а значит нужно разбиратся с конфигурацией, кто и зачем туда лазил и что зделал.

***Разблокировка дублей username автоматическая:***

- При изменении дат в `config.json` в inbound, в `full_username` будет без проблем произведена очистка только этого пользователя из правила блокировки так как каждый раз происходит собирание массива заблокированных пользователей заново не обращая внимания на дублирование.
- При удалении трафика вручную в `TR_DB_M` или автоматом в конце месяца когда у дублей по `username` становится меньше лимита то будут разблокированы все дубли `username` так как каждый раз происходит собирание массива заблокированных пользователей заново а трафик считается по всем дублям `username`.

***Подсчет трафика при дублях***

- в подробной инфе пользователя считает трафик плюсуя трафик по всем совпадениям `username` что бы при изменениях даты у пользователя статистика не сбрасывалась.
- в информации по всем юзерам считает плюсуя трафик по всем совпадениям `username` что бы при изменениях даты стата не сбрасывалась по этому все дубли будут иметь одинаковый общий трафик.
- при авто бане по трафику так же считает по всем пользователям по всем совпадениям `username` и банит все дубли сразу.


**Работа с обычными пользователями**

***Онлайн пользователи особенности подсчета***

В апи пользователь считается оффлайн если не запрашивал соединение 20 секунд.
Так же существует баг из-за которого оффлайн юзеры не становятся оффлайн пока не вызовешь `xray api statsgetallonlineusers` который выведет всех онлайн юзеров и сбросит тех пользователей кто оффлайн в статистике в оффлайн и затем по командам `xray api statsonline --email "$FULL_EMAIL"` && `xray api statsonlineiplist --email "$FULL_EMAIL"` больше не будет значений, хотя будет все равно подписано что они якобы были онлайн.
По этому в скриптах userinfo.sh usershow.sh и system_info.sh сначала всегда идет команда сброса даже если она не нужна что бы онлайн, ip и количество девайсов показало нормально

***Особенности разблокировки пользователей***

- При работе через скрипты бан по траффику/времени снимается сам при добавлении пользователю траффика/времени.
- Но если пользователь забанен одновременно вручную по траффику или вручную то добавить время не получится пока не сбросишь трафик или не разлочишь вручную, на разлок вручную и сброс трафика таких ограничений нет, это ограничение только из-за того что при добавлении времени по факту мы меняем `full_username`.
- Если поправить время вручную в `inbound` в `config.json` то при следующем автозапуске бана по времени пользователь разбанится.
- Если удалить трафик вручную в `TR_DB_M` или месяц сменился и база очистилась то пользователь тоже разбанится при следующем автозапуске бана по траффику.


**Права и пользователи**

***Пользователи и группы***

При установке создается сервисный пользователь с sudo без пароля - service_user_********
Для доступа по ssh создается группа, кроме нее никто не может логинится - ssh_users
Для демонов создаются пользователи - xray, telegram_gateway с общей группой xray_read_write_group

***Файлы и права***

- Скрипты уведомлений /usr/local/bin/telegram
- Скрипты сервисные /usr/local/bin/service
- Библиотеки скриптов /usr/local/lib/service
- Xray /usr/local/bin/xray
- data /usr/local/share/xray
Все исполняемые файлы и библиотеки root:root 755 - но при запуске всех скриптов идет проверка либо root либо telegram_gateway пользователь

- Логи xray /var/log/xray
Лог директория root:xray_read_write_group 750
Лог файлы xray root:xray_read_write_group 660 - писать в логи нужно как и xray так и telegram_gateway для запуска теста конфигурации при работе с юзерами, по этому вынужденно стоит общая группа, при запуске скриптов от telegram_gateway бота он все равно писать не может но ему нужно открыть этот файл, остальным скриптам не нужны доступ к логам мы пишем в journalctl

- /usr/local/etc/xray
- /usr/local/etc/xray/config.json
- /usr/local/etc/xray/TR_DB_M
- /usr/local/etc/xray/TR_DB_Y
- /usr/local/etc/xray/URI_DB
Папка с всеми конфигурациями и базами root:xray_read_write_group 770, нам нужно создавать другие файлы бекапы по этому ставим право писать в папку и группу
Файлы все имеют root:telegram_gateway 660 что бы писать могли только скрипты, только конфигурация имеет root:xray_read_write_group 660 так как нам в нее писать нужно через скрипты а xray читать
